# Track boundaries

The **Track boundaries** module visualizes nearby invisible-wall and kart-mask respawn colliders during an offline race. Enable the module in Toolkit settings and press **F10** to open or close the full inspector, including its in-game controls. It starts closed. While open, the cursor is unlocked; **F10**, **Esc**, or the close button closes the inspector and restores the prior cursor state. **F8** selects the collider under the screen center for a details readout. Cyan marks invisible walls; orange marks colliders in the local kart's unconditional or flat/angle-dependent respawn masks. Translucent surfaces, opacity, view range and outline cap are adjustable in the panel. X-ray has been removed so outlines remain depth-tested and scenery stays visible.

## Zero-count correction in 0.6.12

The player's 0.6.11 screenshot showed the module ON with zero walls and zero respawn meshes. That version required a `PTK_HideMeshRendererInPlayMode` component, a mesh renderer/filter, an original material, and a collider in a particular subtree. It also restricted scene membership. Those requirements were stronger than the game's collision rules and excluded valid boundaries.

The corrected module inventories active colliders across loaded scenes, including additive scenes. The local kart's actual three wall/respawn layer masks determine selection; names, tags and debug-hiding components are unnecessary. Respawn masks take precedence over wall effects. Player-owned colliders, disabled/inactive objects and unrelated collider layers are excluded. A wall whose enabled renderer already draws the same collision mesh is skipped as visible scenery. Flat respawn boundaries are displayed even when their angle condition would not currently cause a reset.

For a MeshCollider the view shares `MeshCollider.sharedMesh`, including when there is no renderer, filter or original material. It does not read vertex arrays from an unreadable native mesh. Box, sphere and capsule colliders get generated visual meshes from their collider dimensions and center. Round volumes account for nonuniform world scale and capsule direction. They are polygonal visualizations, not a reconstruction of PhysX's cooked collision surfaces; convex MeshColliders can also have a cooked hull different from their source mesh.

Native IL2CPP downcasts use `TryCast<T>`: a base Collider wrapper need not be a managed MeshCollider instance. Each collider has its own view, so multiple colliders on one object are not collapsed into a single renderer.

## Drawing and lifecycle

The 0.6.12 player screenshots confirmed detection on two tracks but showed cyan/orange washes across the entire scene. Filled double-sided volumes with depth testing set to Always accumulate over scenery, especially while the camera is inside a large respawn volume. The native scenery was not made transparent; the added filled overlays obscured it.

Runtime 0.6.13 draws mesh edges instead of filled surfaces. Runtime 0.6.14 keeps that default and makes X-ray an explicit opt-in (`CompareFunction.Always`); pressing F9 switches back to depth-tested `LessEqual`. The added MeshRenderer is disabled; shared geometry is drawn explicitly in the existing StudioBehaviour's OnRenderObject callback for Game cameras that include Default. Mesh/box views follow the source transform; sphere/capsule views follow the source world center, orientation and effective radius. All native submeshes are drawn, including unreadable meshes, without extracting CPU vertex/index data. Cyan/orange line opacity is 0.85, and depth writing is disabled where the shader exposes these properties. Missing geometry/material support is counted.

The 0.6.14 draw list is rebuilt at the existing one-second selection interval, sorted by distance to any local kart, and capped before creating view objects. A conservative projected-bounds check skips offscreen shapes in the camera callback. `MaxVisibleColliders` defaults to 64 and is bounded to 16–192. F8 pins the closest visible selected collider intersected by a ray from viewport center; its outline is yellow and the panel reports shape, object name, layer, kart distance and world bounds. The pin consumes one slot in the normal draw cap. These limits bound overlay work; they do not change physics or reduce the game's own collider count.

In 0.6.15, **Translucent surfaces** defaults off. When enabled, each selected volume gets a separate fill pass before its wireframe outline. Fill material uses alpha blending, no depth writes, back-face culling and the same depth test as outlines; F9 X-ray applies to both passes. Opacity defaults to 0.12 and ranges from 0.03 to 0.35. This avoids the earlier opaque-looking, double-sided Always-test wash while preserving an optional shape-volume view. Overlapping transparent colliders can still accumulate color, so keep opacity low on dense tracks. The in-game F7 window changes settings live and saves them through the existing conflict-aware config path; controls also remain available in Toolkit settings.

Wireframe rasterization is scoped around only the module's immediate mesh draws. A finally block restores the prior GL.wireframe value on success or failure, so native objects and the HUD keep their existing raster state. Rendering failure removes the owned visuals and logs once. Unity documents this state as global until restored; the current player's log confirms Direct3D 11. The implementation uses [GL.wireframe](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/GL-wireframe.html), [OnRenderObject](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/MonoBehaviour.OnRenderObject.html) and [Graphics.DrawMeshNow](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Graphics.DrawMeshNow.html). Wireframe support and callback availability differ on other graphics APIs/render pipelines; this is not a cross-platform certification.

Existing colliders, collision layers, native renderers/materials, cameras, track transforms and game debug flags stay untouched. No collider or physics mesh is created or rebaked. Only generated visual meshes are destroyed; native shared meshes are retained. Hiding, disabling, leaving the race, entering online play, changing maps and unloading remove the module's visual objects and materials. A camera that excludes Default will not show them; camera masks are never expanded.

The active collider inventory refreshes every five seconds. Selection/range checks run once a second; selected volumes follow their transforms each frame. No scene scanning occurs in menus. The HUD identifies the two categories, selection count, draw cap and camera draw count. The F10 inspector panel controls wall/respawn visibility, surfaces, opacity, distance and cap. Checked controls use a custom high-contrast green checkmark, and both inspector and camera panels use a solid dark background for legibility. A zero result includes mask matches, out-of-range matches and already-visible walls; the log also records inventory size and the kart's exact three masks.

**Respawn colliders** and **pinning** are different concepts. The orange category selects colliders matching the kart controller's native respawn layer masks. Pinning does not classify or enable anything: F8 only selects one already-displayed collider to show its name, shape, layer, distance and bounds. A track area that causes a respawn without an orange shape is outside the current mask-based coverage, or its collider is unsupported, outside the view range/cap, hidden behind scenery, or otherwise not selected. The game also contains a generic `PTK_ModTKLogic_PhysicsTrigger` system with trigger layers and data, but the recovered evidence does not establish which of those triggers cause respawns. The inspector intentionally does not draw every generic trigger as a respawn collider, because that would mislabel unrelated gameplay triggers. Identifying those missing authored areas requires inspecting the track's trigger-type data or tracing the trigger callback for the relevant track.

**Disable this module for performance captures.** Rendering boundary geometry adds work. Performance diagnostics records whether the view was visible.

## Validation boundary

Earlier production-linked checks cover collider selection, native wrapper casts, geometry, range changes, cleanup and scoped wireframe drawing. No cited screenshot validates the 0.6.14–0.6.16 rendering or GUI in-game. Offline acceptance should confirm F10 open/close, center-ray selection, checked-state visibility, opaque panel readability, fill opacity, cursor restoration, camera callback behavior and the cap on the player's tracks. No performance improvement to the game itself is claimed; the cap only bounds this diagnostic overlay's cost.
